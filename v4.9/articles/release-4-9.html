SQL Server

Binärspalten (Bilder, Dateien) wurden von FS bislang immer als veralteter Typ image neu angelegt. Der image Datentyp ist seit 2006 deprecated.

Note

Ab FS 4.9 wird nun der varbinary(max) Datentyp verwendet. Die Differenzlogik erkennt diesen Fall und bietet eine automatische Konvertierung im DBDifferenceAnalyzeMode.Cleanup an.

Warning

Die erstellten SQL-Skripte mit dem Modus DBDifferenceAnalyzeMode.Cleanup sollten niemals automatisch ausgeführt werden, da dieser Modus wortwörtlich einen Cleanup durchführt. Indizes, die nur in der Datenbank vorkommen, nicht jedoch in Framework Studio definiert sind, werden dabei tatsächlich gelöscht.

Verwaiste Tabellen und Spalten werden dagegen ausschliesslich zur Information gemeldet - für sie erzeugt FS bewusst kein DROP-Skript (siehe Verwaiste Tabellen und Spalten).

FSROWID wird als uniqueidentifier verglichen

Unter SQL Server werden FSROWID-Spalten als uniqueidentifier angelegt. Die Differenzlogik hat als Wunschtyp bislang jedoch Integer angenommen. Ab FS 4.9 wird korrekt Guid (uniqueidentifier) erwartet.

Note

Diese Korrektur gehört zur unten beschriebenen neuen Guid-Prüfung: Ohne sie würde für jede bestehende FSROWID-Spalte eine nicht auflösbare Abweichung (Unsolvable) gemeldet, weil uniqueidentifier nicht automatisch nach int konvertierbar ist.

Verwaiste Tabellen und Spalten

Tabellen und Spalten, die in der Datenbank vorhanden sind, in Framework Studio aber nicht (mehr) definiert sind, gelten als verwaist. Sie werden ab FS 4.9 im Modus DBDifferenceAnalyzeMode.Cleanup als Abweichung der Kategorie Cleanup aufgelistet.

Important

Verwaiste Tabellen und Spalten werden mit IsActive = false gemeldet. Sie erscheinen also im Report, es wird aber kein DROP-Skript für sie erzeugt. Ob und wie sie entfernt werden, entscheidet bewusst der Anwender.

Für verwaiste Spalten ist keine zusätzliche Konfiguration erforderlich.

Für verwaiste Tabellen muss der Aufrufer DBAnalyzeOptions.KnownTableNames befüllen. Erwartet wird die Vereinigung der Tabellennamen aller FS-Connections, die sich dieselbe physische Datenbank bzw. dasselbe Schema teilen - beispielsweise mehrere logische Connections auf derselben PostgreSQL-Datenbank.

var options = new DBAnalyzeOptions
{
    Mode = DBDifferenceAnalyzeMode.Cleanup,
    // Tabellen aller Connections, die sich Datenbank/Schema teilen
    KnownTableNames = allTableNamesOfSharedSchema
};

Zum Verhalten der Prüfung:

  • Bleibt KnownTableNames auf null, findet keine Verwaisungsprüfung für Tabellen statt. Andernfalls würden Tabellen anderer, legitimer Connections fälschlich als verwaist gemeldet.
  • Ausserhalb von DBDifferenceAnalyzeMode.Cleanup entfällt die Prüfung ebenfalls.
  • Die FS-internen dbRun_*-Tabellen werden nie als verwaist gemeldet.
  • Der Vergleich der Tabellennamen läuft über den Comparer des Adapters und ignoriert damit standardmässig die Gross-/Kleinschreibung. Das betrifft ausschliesslich den Metadaten-Abgleich der Namen und ist unabhängig davon, wie die Datenbank Dateninhalte vergleicht (siehe Gross-/Kleinschreibung bei String-Vergleichen).

Weitere Verbesserungen bei Differenzlogik

Zusätzlich wird nun auch im Cleanup Modus ausgegeben, wenn statt datetime datetime2 als SQL-Datentyp verwendet wird. Diese Datenbankspalten sollten zu datetime konvertiert werden.

Des Weiteren werden jetzt auch Abweichungen bei Boolean (bit), Byte (tinyint), Guid (uniqueidentifier) und Gleitkommazahlen (float/real) erkannt, die vorher unbemerkt geblieben wären.

Note

Als passend gelten dabei alle nativen Typen, die FS für den jeweiligen Datentyp akzeptiert - bei Boolean etwa char, nchar und bit, bei Single/Double float und real. Native Typen mit fester Präzision (decimal, numeric) gelten unter einem Single- oder Double-Feld dagegen als nicht automatisch konvertierbar und werden als Unsolvable gemeldet, da eine Umstellung auf float Präzision verlieren kann. Solche Spalten müssen manuell bewertet werden.
