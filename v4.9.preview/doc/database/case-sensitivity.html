Groß-/Kleinschreibung bei String-Vergleichen

Ob ein String-Vergleich (=, LIKE, ORDER BY, DISTINCT, Unique-Index) die Groß-/Kleinschreibung beachtet, legt die Datenbank fest — nicht Framework Studio. Das Verhalten unterscheidet sich deshalb je nach eingesetztem Datenbanksystem.

Übersicht

Datenbank Gleichheit (=, LIKE, Unique) Sortierung (ORDER BY)
SQL Server abhängig von der Instanz-Collation; bei den üblichen Defaults (Latin1_General_CI_AS, SQL_Latin1_General_CP1_CI_AS) case-insensitiv case-insensitiv
Oracle case-sensitiv (NLS_COMP=BINARY, Oracle-Default) case-insensitiv (Framework Studio setzt NLS_SORT=BINARY_AI)
PostgreSQL case-sensitiv (Default-Collation der Datenbank) abhängig von der Default-Collation der Datenbank
Important

Dieselbe Anwendung kann auf SQL Server also andere Suchergebnisse liefern als auf Oracle oder PostgreSQL. Soll eine Suche auf allen Datenbanken gleich funktionieren, muss sie explizit case-insensitiv formuliert werden (siehe Best Practices).

PostgreSQL

Framework Studio legt String-Spalten (character varying, text) ohne explizite Collation an. Damit gilt die Default-Collation der Datenbank, und die ist deterministisch — Gleichheit heißt Byte-Gleichheit:

SELECT * FROM customer WHERE name = 'Max';    -- findet 'Max', nicht 'max' oder 'MAX'
SELECT * FROM customer WHERE name LIKE 'ma%'; -- findet 'max', nicht 'Max' oder 'MAX'

Das gilt gleichermaßen für DISTINCT, GROUP BY, IN und Unique-Indizes: 'ABC' und 'abc' sind zwei verschiedene Werte und damit auch zwei verschiedene Schlüssel.

Sortierung (ORDER BY)

Die Reihenfolge hängt an der Default-Collation, die bei der Anlage der Datenbank festgelegt wird:

  • C / POSIX — reine Byte-Reihenfolge. Alle Großbuchstaben kommen vor allen Kleinbuchstaben: MAX < Max < max, und Z < a. Umlaute landen hinter allen ASCII-Zeichen.
  • libc-Locales wie de_DE.utf8 / en_US.utf8 und ICU-Locales — sprachliche Sortierung. Groß- und Kleinschreibung wird pro Buchstabe gruppiert, die Kleinschreibung kommt dabei zuerst: max < Max < MAX. Umlaute werden sprachlich einsortiert (im Deutschen ä bei a), nicht hinten angehängt.
Note

Die Reihenfolge zwischen Groß- und Kleinschreibung ist damit genau umgekehrt zu C. Wer sich auf eine konkrete Reihenfolge verlässt, sollte sie gegen die tatsächlich eingesetzte Default-Collation prüfen (SELECT datcollate, datctype FROM pg_database WHERE datname = current_database();).

Legt Framework Studio die Datenbank selbst an (z. B. über den Runtime-Repository-Wizard), wird CREATE DATABASE ohne Collation-Angabe ausgeführt — die Datenbank erbt damit die Vorgabe des Servers (template1), analog zum Vorgehen bei SQL Server. Wenn eine reproduzierbare Sortierung wichtig ist, sollte die Datenbank stattdessen vorab mit expliziter Collation angelegt werden:

CREATE DATABASE mybusinessdb
    ENCODING 'UTF8'
    LOCALE_PROVIDER icu
    ICU_LOCALE 'de-DE'
    TEMPLATE template0;

Unabhängig von der Default-Collation kann die Reihenfolge pro Abfrage erzwungen werden:

SELECT name FROM customer ORDER BY name COLLATE "C";   -- Byte-Reihenfolge
SELECT name FROM customer ORDER BY UPPER(name);        -- Groß-/Kleinschreibung ignorieren

Oracle

Oracle vergleicht mit den Standardeinstellungen (NLS_COMP=BINARY) ebenfalls case-sensitiv. Framework Studio setzt beim Verbindungsaufbau lediglich NLS_SORT (Default BINARY_AI); das wirkt bei NLS_COMP=BINARY ausschließlich auf die Sortierung, nicht auf Gleichheitsvergleiche:

  • WHERE name = 'Max' findet nur 'Max' — nicht 'max' oder 'MAX'.
  • ORDER BY name sortiert case- und akzent-insensitiv (BINARY_AI), Umlaute werden also wie ihr Grundbuchstabe einsortiert.

Das gesamte NLS-Setup (NLS_COMP, NLS_SORT, NLS_CHARACTERSET) liegt beim Datenbank-Administrator. Framework Studio legt auf Oracle keine Datenbank an und verändert NLS_COMP nicht.

Best Practices

Case-insensitive Suche: UPPER() bzw. LOWER()

Ein Vergleich, der auf allen Datenbanken case-insensitiv ist, muss die Groß-/Kleinschreibung auf beiden Seiten vereinheitlichen:

WHERE UPPER(name) = UPPER('Max')
WHERE UPPER(name) LIKE UPPER('ma%')

UPPER() auf nur einer Seite reicht nicht — der Suchwert muss ebenso umgewandelt werden.

Tip

PostgreSQL kennt zusätzlich ILIKE als case-insensitives LIKE. Das ist nicht portabel und sollte in Anwendungscode, der auch auf SQL Server oder Oracle laufen soll, nicht verwendet werden.

SearchOperator LikeNonCaseSensitive

Für Suchfelder in Forms gibt es den Weg über die Metadaten, ohne selbst SQL zu schreiben: die Control-Eigenschaft SearchOperator kennt den Wert LikeNonCaseSensitive. Der Generator erzeugt daraus genau das oben beschriebene Muster:

UPPER(spalte) LIKE UPPER('wert%')

Damit verhält sich das Suchfeld auf allen drei Datenbanken identisch. Der Default-Wert von SearchOperator ist Equal — ein Suchfeld ist also standardmäßig abhängig vom eingesetzten Datenbanksystem. Soll eine Suche unabhängig von der Groß-/Kleinschreibung funktionieren, muss LikeNonCaseSensitive bewusst gesetzt werden.

Indizes

UPPER(spalte) bzw. LOWER(spalte) verhindert die Nutzung eines normalen Index auf spalte — die Datenbank müsste für jede Zeile erst den Funktionswert berechnen. Für häufig genutzte case-insensitive Suchen sollte deshalb ein funktionaler Index angelegt werden, der zur Suchbedingung passt:

-- PostgreSQL
CREATE INDEX idx_customer_name_upper ON customer (UPPER(name));

-- Oracle
CREATE INDEX idx_customer_name_upper ON customer (UPPER(name));

Zu beachten:

  • Der Index muss exakt die Funktion der Suchbedingung verwenden. Ein Index auf UPPER(name) hilft einer Suche mit LOWER(name) nicht.
  • Eine Suche mit führendem % (LIKE '%wert%', also FullTextSearch am Control) kann keinen B-Tree-Index nutzen — auch keinen funktionalen. Für solche Suchen sind in PostgreSQL Trigram- Indizes (pg_trgm) eine Option.
  • Funktionale Indizes werden nicht über den Datenbank-Abgleich verwaltet und müssen vom Datenbank-Administrator angelegt werden.

Case-sensitive Eindeutigkeit

Da Gleichheit case-sensitiv ist, verhindert ein Unique-Index auf einer String-Spalte nicht, dass 'ABC' und 'abc' beide angelegt werden. Soll die Eindeutigkeit die Groß-/Kleinschreibung ignorieren (typisch für Dublettenprüfungen auf Schlüsselfeldern), braucht es einen funktionalen Unique-Index:

CREATE UNIQUE INDEX idx_customer_code_ci ON customer (UPPER(code));
