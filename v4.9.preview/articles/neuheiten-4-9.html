Neuheiten Framework Studio 4.9

Informationen zu aktuellen Versionen und korrigierten Fehlern finden Sie in den Release-Informationen.

Update DLLs

Mit Framework Studio 4.9 wurden die Versionen aller referenzierten Pakete aktualisiert.

Dadurch kann es beim Compile eigener Anwendungen zu neuen Errors oder Warnings kommen, wenn eingebundene Ressourcen (DLLs) nicht mehr zu den aktualisierten Versionen passen. Details zur Ursache und zur Behebung solcher Meldungen finden Sie unter Referenz-Prüfung für Ressourcen.

PostgreSQL als neue unterstützte Anwendungsdatenbank

Neben SQL Server und Oracle unterstützt Framework Studio nun auch PostgreSQL (ab Version 18) als Datenbankplattform für Anwendungen.

Note

PostgreSQL wird ausschließlich für die Anwendungsdatenbank (Database) und die Runtime-Datenbank unterstützt. Als Repository-Datenbank der Framework Studio IDE steht weiterhin nur SQL Server oder Oracle zur Verfügung.

Einrichtung

Eine PostgreSQL-Datenquelle wird wie gewohnt über den neuen Connection Type PostgreSql angelegt (siehe Datasource und Connection Einstellungen).

Important

Vor der ersten Verwendung muss ein Datenbank-Administrator einmalig einen impliziten Typ-Cast auf der PostgreSQL-Datenbank anlegen. Details dazu und zu weiteren Besonderheiten (Identifier-Groß-/Kleinschreibung, Groß-/Kleinschreibung bei Vergleichen) siehe PostgreSQL-Connection - Datenbank einrichten.

Besonderheiten gegenüber SQL Server

  • Windows-Authentifizierung wird nicht unterstützt - es wird immer Username/Password verwendet.
  • PostgreSQL ist nativ UTF-8, die Unterscheidung zwischen String und AnsiString entfällt serverseitig.
  • Zeilenversionierung ist durch das native MVCC immer aktiv, eine explizite Konfiguration wie bei SQL Server ist nicht nötig (siehe Zeilenversionierung).
  • String-Vergleiche sind case-sensitiv - anders als bei den üblichen SQL-Server-Collations, aber wie bei Oracle (siehe Groß-/Kleinschreibung bei String-Vergleichen).

Fehlerverhalten innerhalb von Transaktionen

Caution

PostgreSQL verhält sich bei Fehlern innerhalb einer offenen Transaktion fundamental anders als SQL Server.

Bei SQL Server bleibt eine Transaktion nach einem fehlgeschlagenen Statement (z.B. ein SELECT auf eine nicht existierende Tabelle) weiterhin nutzbar - nachfolgende Statements werden normal ausgeführt, sofern der Fehler im Code abgefangen wird.

Bei PostgreSQL wird die gesamte Transaktion nach dem ersten Fehler als aborted markiert. Jedes weitere Statement in dieser Transaktion schlägt fehl mit 25P02: current transaction is aborted, commands ignored until end of transaction block, bis ein ROLLBACK ausgeführt wird - unabhängig davon, ob der ursprüngliche Fehler im Code abgefangen wurde.

Eigener Code, der nach dem Muster "Fehler abfangen und in derselben Transaktion weiterarbeiten" implementiert ist (z.B. per Try/Catch prüfen, ob eine Tabelle existiert, und bei Fehler mit anderer Logik fortfahren), funktioniert deshalb auf SQL Server, schlägt auf PostgreSQL aber mit 25P02 fehl, sobald ein weiteres Statement in derselben Transaktion ausgeführt wird.

Tip

Prüfen Sie vor einem potenziell fehlschlagenden Statement die Voraussetzung explizit (z.B. Existenz einer Tabelle über information_schema), statt auf einen Fehler zu reagieren und in derselben Transaktion fortzufahren.

Impliziter Typ-Cast

Important

Vor der ersten Verwendung muss ein Datenbank-Administrator (Superuser) einmalig einen Cast auf der PostgreSQL-Datenbank anlegen.

SQL Server konvertiert bei Vergleichen automatisch zwischen String- und numerischen Typen (z.B. smallint = varchar). PostgreSQL tut das grundsätzlich nicht und benötigt dafür einen expliziten Cast:

CREATE CAST (character varying AS numeric) WITH INOUT AS IMPLICIT;

Ohne diesen Cast schlagen Queries fehl, die numerische Spalten mit String-Parametern vergleichen - ein Fehler, der bei Tests auf SQL Server nie auffällt, da dort die Konvertierung transparent passiert. Framework Studio prüft beim Start, ob der Cast vorhanden ist, und meldet einen Fehler, falls nicht. Details siehe PostgreSQL-Connection - Datenbank einrichten.

Caution

Es darf nur dieser eine Cast angelegt werden. Mehrere oder bidirektionale Casts führen zu operator is not unique-Fehlern.

Groß-/Kleinschreibung bei String-Vergleichen

PostgreSQL vergleicht Strings case-sensitiv (=, <, >, LIKE, DISTINCT, Unique-Indizes). Framework Studio setzt keine Collation auf String-Spalten, es gilt also die Default-Collation der Datenbank:

SELECT * FROM customer WHERE name = 'Max';    -- findet 'Max', nicht 'max' oder 'MAX'
SELECT * FROM customer WHERE name LIKE 'ma%'; -- findet 'max', nicht 'Max' oder 'MAX'
  • Unterschied zu SQL Server: Dort ist Case-Insensitivität keine Eigenschaft von Framework Studio, sondern von der Instanz-Collation des Kunden (üblicherweise Latin1_General_CI_AS). Auf Oracle sind Gleichheitsvergleiche mit den Standardeinstellungen dagegen ebenfalls case-sensitiv - PostgreSQL verhält sich hier also wie Oracle.
  • Case-insensitive Suche: Wo Groß-/Kleinschreibung ignoriert werden soll, muss der Vergleich das explizit tun - über UPPER()/LOWER() auf beiden Seiten oder über die Control-Eigenschaft SearchOperator = LikeNonCaseSensitive, die genau dieses SQL generiert.
  • Sortierung: Die Reihenfolge bei ORDER BY hängt an der Default-Collation der Datenbank. Bei C/POSIX gilt die Byte-Reihenfolge (MAX < Max < max), bei libc-/ICU-Locales wird sprachlich sortiert.
  • Indizes: UPPER(spalte) kann keinen normalen Index nutzen. Für häufige case-insensitive Suchen ist ein funktionaler Index (CREATE INDEX ... ON t (UPPER(spalte))) nötig.

Details und Best Practices siehe Groß-/Kleinschreibung bei String-Vergleichen.

Identifier-Groß-/Kleinschreibung

PostgreSQL verhält sich analog zu Oracle: Unquotierte Identifier werden normalisiert - Oracle auf GROSSSCHREIBUNG, PostgreSQL auf Kleinschreibung. Quotierte Identifier ("MeineTabelle") bleiben dagegen case-sensitiv. SQL Server ist case-preserving.

Framework Studio berücksichtigt das automatisch (alle generierten Identifier werden konsistent kleingeschrieben und quotiert). Relevant wird es, wenn Tabellen/Spalten außerhalb von Framework Studio angelegt werden - z.B. durch Migrationswerkzeuge (siehe unten) - und dabei gemischte Schreibweise entsteht: Ein unquotiertes SELECT * FROM MeineTabelle findet dann meinetabelle nicht.

Datums-/Zeitwerte

Neuere Npgsql-Versionen mappen DateTime-Parameter standardmäßig auf timestamp with time zone. Framework Studio verwendet intern durchgängig timestamp without time zone (entspricht dem SQL Server datetime-Verhalten) und aktiviert dafür automatisch das Npgsql-Legacy-Timestamp-Verhalten. Für reinen Framework-Studio-Code ist das transparent - relevant wird es nur, wenn eigener Code direkt mit der Npgsql-API oder rohen Timestamp-Literalen arbeitet.

GETGUID()

GETGUID() liefert auf PostgreSQL - wie auf SQL Server und Oracle - einen 32-stelligen lowercase Hex-String ohne Bindestriche, nicht das native PostgreSQL-Format des uuid-Typs (mit Bindestrichen). Das ist bewusst so gewählt, damit Anwendungscode unabhängig vom Connection Type mit demselben GUID-Format arbeitet.

Views beim DB-Abgleich

PostgreSQL verbietet ALTER TABLE ... ALTER COLUMN ... TYPE ... auf Spalten, die von einer View referenziert werden (0A000: cannot alter type of a column used by a view or rule). SQL Server erlaubt Typänderungen in diesem Fall. Framework Studio behandelt das beim DB-Abgleich automatisch: abhängige Views werden vor der Typänderung gedroppt und danach wiederhergestellt.

Migration von SQL Server oder Oracle

Framework Studio liefert kein eigenes Migrationswerkzeug für den Umstieg von bestehenden SQL Server- oder Oracle-Datenbanken auf PostgreSQL. Der Einsatz von PostgreSQL ist primär für neue Installationen vorgesehen. Am Markt verfügbare Werkzeuge (z.B. pgLoader, AWS SCT, ora2pg) wurden nicht offiziell auf Kompatibilität mit den FS-spezifischen Strukturen (Datentypen, Trigger, Constraints, Collation) geprüft.
