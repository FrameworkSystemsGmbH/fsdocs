Tools des MCP-Servers

Alle Tools des MCP-Servers arbeiten read-only — es werden keine Änderungen am Repository vorgenommen. Jedes Tool meldet das über seine Annotations: readOnlyHint (verändert nichts), idempotentHint (gleiche Argumente, gleiches Ergebnis) und openWorldHint: false (greift nur auf das lokale Repository zu), dazu ein title für die Anzeige im Client.

Die Ergebnisse umfassen standardmäßig die gesamte Package-Hierarchie (aktives Package und dessen Basis-Packages) und lassen sich über den packageScope-Parameter gezielt eingrenzen.

Tip

Die vollständige Parameterbeschreibung jedes Tools wird vom MCP-Server über tools/list bereitgestellt. KI-Clients erhalten diese automatisch bei der Verbindung.

Package-Scope

Die auflistenden und suchenden Tools (fs_list, fs_search_names, fs_search_code, fs_search_dependencies, fs_search_documentation, fs_get_checkin_history) akzeptieren einen optionalen packageScope-Parameter, um die Ergebnisse auf ein Package der aktiven Hierarchie zu beschränken:

Wert Bedeutung
all (Default) Gesamte Hierarchie — aktives Package und alle Basis-Packages
active Nur das aktive (oberste) Package
Package-Name Genau dieses Package der Hierarchie (z.B. eNVenta)
  • Der Package-Name wird strikt verglichen (case-sensitive). Ein unbekannter Wert liefert einen Fehler mit der Auflistung der verfügbaren Packages.
  • Elemente ohne zugeordnetes Package werden außer bei all ausgeblendet.
  • Bei fs_list wird packageScope für datasource und package ignoriert.
Note

Bei fs_get_checkin_history liefert jedes Package der Hierarchie die CheckIns seines aktuellen Labels. Ein importiertes Basis-Package enthält keine CheckIns, sondern nur die importierten Stände; das Ergebnis weist dann mit historyAvailable: false darauf hin (siehe Historie importierter Packages).

Elemente lesen

DevObjects (Component, Form, Service, ServiceHost, Modular Component, Code File)

Tool Beschreibung
fs_get_devobject Details zu DevObjects abrufen. Parameter: elementType (component|form|service|service_host|modular_component|code_file), fullName, detail (optional: summary|full, Default summary), method (optional: nur diese Methode mit vollem Code, siehe Methoden adressieren), property (optional: nur diese Property; nicht für service, service_host und code_file), package (optional: Version des Elements aus einem bestimmten Package der Vererbungskette).
  • Detail-Level: summary (Default) zeigt die Struktur (Property-Namen und -Typen, Methoden-Signaturen) ohne Code-Bodies — ideal zur Orientierung in großen Components. full gibt das komplette YAML mit allen Code-Bodies aus.
  • Components umfassen auch Collections und TextCollections.
  • Forms: Die Ausgabe enthält die Benutzerdokumentation (userDoc) nur ohne method/property; eine gezielte Methoden- oder Property-Abfrage bleibt dadurch schlank.
  • ServiceHosts liefern Service-/ServiceContract-Referenzen, Base-Adresse, Endpoints und Methoden. Methoden und Endpoints werden pro Package ausgegeben: Ein Customizing-ServiceHost zeigt nur seine eigenen. Die eines Basis-Packages liefert der Parameter package, die vollständige Endpoint-Liste fs_get mit elementType=service_host.
  • Basis-Packages: Ein Customizing gibt nur die Methoden des eigenen Packages aus. Methoden, die nur in einem Basis-Package definiert und nicht überschrieben sind, liefert der Parameter package mit dem Namen dieses Packages. Den passenden Namen nennt packageName in den Treffern von fs_search_code und fs_search_names.

Controls in Forms

Feld Bedeutung
visibleAU / editableAU AccessUnits (Name und Berechtigungsmodus), die Sichtbarkeit bzw. Bearbeitbarkeit des Controls steuern. Fehlt der Schlüssel, ist das Control in dieser Hinsicht nicht durch AccessUnits eingeschränkt. Ausgeblendet bzw. gesperrt wird ein Control nur, wenn mindestens eine AccessUnit aufgeführt ist und keine davon gewährt wird.
mappedDBColumn Die physische Datenbankspalte, an die das Control über seine Datenquelle gebunden ist.

Code Files

Bei elementType=code_file trifft der Parameter method alle Member mit Code-Body — Methoden, Konstruktoren, Destruktoren, Operatoren, Konvertierungsoperatoren, Indexer, Properties (get/set) und Events mit add/remove, nicht aber Felder und Event-Felder. Akzeptiert werden der Name und die eindeutige Deklaration (z.B. Bar(int), IFoo.Bar(int), operator +(Money, Money), implicit operator Money(decimal), this[int]), die unverändert verglichen werden. Jeder Treffer trägt enclosingType (z.B. Outer.Inner).

Die eindeutige Deklaration ist nur innerhalb des umschließenden Typs eindeutig: Deklarieren mehrere Typen eines Code Files denselben Member, werden alle geliefert. Ein reiner Name trifft alle gleichnamigen Member über alle Typen hinweg.

Methoden adressieren

Die Tools fs_get_devobject (Parameter method), fs_get_method_history und fs_diff_method (Parameter methodName bzw. declaration) akzeptieren eine Methode in drei Formen:

Form Beispiel
Methodenname Load; für Konstruktoren .ctor oder der Klassenname
Eindeutige Deklaration, wie sie fs_search_code und detail=summary ausgeben Load(FSstring, FSlong), Konstruktor .ctor(FSint)
Vollständige Deklaration mit Rückgabetyp virtual int Load(FSstring sType, FSlong lngId)
  • Beim Vergleich werden Parameternamen, Leerzeichen, Groß-/Kleinschreibung, global::, System-Aliase (Int32 = int) und Namespace-Qualifizierung (NV.Sales.Order = Order) ignoriert.
  • Eine vollständige Deklaration ohne Rückgabetyp gilt als Konstruktor und schlägt fehl, wenn ihr Name nicht der Klassenname ist.
  • Der Rückgabetyp gehört nicht zur Identität der Methode: Weicht ein angegebener Rückgabetyp vom gespeicherten ab, wird die Methode trotzdem verwendet und note weist darauf hin.
  • Bei fs_get_devobject liefert ein reiner Name alle Überladungen; eine eindeutige oder vollständige Deklaration muss genau eine Methode treffen.
  • Bei fs_get_method_history und fs_diff_method bricht ein reiner Name, der in einer der betrachteten Versionen mehrere Überladungen trifft, mit der Liste der Kandidaten ab. Mit declaration wird die Überladung gezielt gewählt; die Angabe hat Vorrang vor methodName und muss denselben Namen tragen.
  • Wird eine angefragte Methode nicht gefunden, listet die Fehlermeldung von fs_get_devobject die im abgefragten Package vorhandenen Methoden mit ihrer eindeutigen Deklaration auf („Available methods in this package: …“), sodass kein zusätzlicher summary-Aufruf nötig ist. Bei Customizings folgt ein Hinweis auf den Parameter package, da geerbte Methoden nicht aufgeführt werden. Bei Code Files nennt die Fehlermeldung stattdessen die Arten von Membern, die der Filter trifft.

Gelesene Schicht bei Customizings

fs_get_devobject und fs_get geben im Kopf des Ergebnisses an, welche Schicht der Customizing-Kette gelesen wurde:

Feld Bedeutung
packageName Package, aus dem der gelieferte Inhalt stammt
layer own (eigenes Element) oder customization (Customization eines Elements aus einem Basis-Package)
isActivePackage Ob die gelesene Schicht im aktiven Package liegt. Mit package auf ein Basis-Package ist der Wert false.
baseLayers Nur bei einer Customization: die Schichten darunter, die oberste zuerst

Method Observer

Überschriebene Member mit einer Basis tragen in der Ausgabe von fs_get_devobject die Angaben des Method Observers: observer bei Methoden, getObserver/setObserver bei Properties. Sie enthalten active (ob der Observer aktiv ist) und, wenn sich Basis-Member seit dem Aktivieren geändert haben, warnings je Package — dieselbe Information wie die Warnung FSWarn[2029] in der IDE.

Suche

Tool Beschreibung
fs_search_names Element-Namen und FullNames durchsuchen (alle Elementtypen inkl. Code Files). Parameter: query, caseSensitive, elementType (optional, PascalCase, z.B. Component, CodeFile), packageScope, maxResults (Default 50).
fs_search_code Volltextsuche in Signatur und Rumpf der Methoden von Components, Forms, Services, Modular Components, Global Events, Service Contracts und Service Hosts sowie im Quelltext von Code Files. Alle Überladungen einer Methode werden durchsucht. Parameter: query, regex (optional: false für Literal-Match, true für Regex-Pattern), caseSensitive, packageScope, namespaceName, elementType, maxResults (Default 50).
fs_search_dependencies Strukturelle Abhängigkeiten eines Elements finden (Properties, Typen, Vererbung). Parameter: fullName, packageScope, maxResults (Default 100).
fs_search_documentation MLDoc-Felder auf Metadatatypes, Properties, Forms und DocumentationOwnern durchsuchen. Parameter: query, caseSensitive, packageScope, maxResults (Default 50).

Code-Suche eingrenzen

fs_search_code lässt sich zusätzlich zu packageScope weiter eingrenzen; alle Filter werden per UND verknüpft:

Parameter Bedeutung
namespaceName Namespace inklusive aller Sub-Namespaces. Erwartet den vollqualifizierten Namen, Groß-/Kleinschreibung egal: Trade.Sales trifft Trade.Sales und Trade.Sales.Orders, aber nicht Trade.SalesReport. Anders als bei fs_list wird der Kurzname allein nicht akzeptiert. Ein unbekannter Namespace liefert einen Fehler.
elementType Ein oder mehrere Elementtypen als Liste, z.B. ["component", "code_file"]: component, form, service, modular_component, global_event, service_contract, service_host, code_file. Ein Einzelwert als Text wird ebenfalls akzeptiert; Unterstriche und Groß-/Kleinschreibung werden toleriert (ModularComponent passt also auch). Andere Typen liefern einen Fehler.

Ungültige Parameter (auch ein nicht übersetzbarer regulärer Ausdruck) werden sofort gemeldet, bevor der Suchindex aufgebaut wird. Reguläre Ausdrücke sind auf 100 ms je Zeile und 10 s je Suche begrenzt; bei Überschreitung hilft ein einfacheres Pattern oder eine engere Eingrenzung.

Ergebnisse der Code-Suche

Jeder Treffer enthält elementFullName, elementType, namespace, packageName, methodName, uniqueDeclaration, lineNumber und matchLine.

  • uniqueDeclaration — die eindeutige Deklaration der Methode bzw. des Members. Sie lässt sich direkt als method an fs_get_devobject übergeben und trifft dann genau diese Methode, auch bei Überladungen. Nur wenn die gespeicherte Deklaration nicht auswertbar ist, ist sie leer; dann hilft methodName.
  • lineNumber — bei Methoden 1-basiert und relativ zum gespeicherten Methodenrumpf. 0 bedeutet einen Treffer in der Signatur; Signaturtreffer stehen vor den Rumpftreffern derselben Methode. fs_get_devobject gibt Methoden neu formatiert und mit Signatur und Klammern aus, die Zeilennummern weichen dort also ab — den Treffer findet man über matchLine. Bei Code Files ist lineNumber relativ zum Member-Quelltext, wie fs_get_devobject ihn ausgibt; eine Zeile 0 gibt es dort nicht.
  • packageName — stammt ein Treffer aus einem Basis-Package, liefert fs_get_devobject die Methode nur mit package=<packageName>, da ein Customizing nur die Methoden des eigenen Packages ausgibt.

Treffer in Global Events und Service Contracts ruft man über fs_get ab: Es gibt alle Methoden mit Deklaration und rohem innerCode aus (dort passt lineNumber direkt), allerdings nur die Version im aktiven Package.

Treffer in Code Files (elementType = "CodeFile") tragen zusätzlich:

  • kind — Art des Members, z.B. method, property, event
  • enclosingType — umschließender Typ (Outer.Inner), zur Unterscheidung gleichnamiger Member in verschachtelten Typen

Methoden-Treffer stehen vor Code-File-Treffern. Bei vielen Methoden-Treffern schneidet maxResults die Code-File-Treffer daher ab — mit elementType: ["code_file"] wird gezielt nur in Code Files gesucht.

Note

fs_search_code durchsucht bei Methoden Signatur (inkl. Parametertypen und -namen) und Rumpf, nicht aber Descriptions. Die Signatur wird dabei vereinheitlicht und einzeilig durchsucht (überzählige Leerzeichen entfernt, ", " nach Kommas) — auch wenn sie in der IDE anders eingegeben wurde, z.B. Load( FSstring a ). Bei Code Files wird jeder Member mit Code-Body durchsucht (Methoden, Konstruktoren, Destruktoren, Operatoren, Indexer, Properties mit get/set, Events mit add/remove), auch in verschachtelten Typen — nicht aber Felder, Event-Felder, Enum-Member, usings und Typdeklarationen.

fs_search_names durchsucht Element-Namen, nicht Property- oder Methodennamen innerhalb eines Elements. AccessUnit, Datasource, DocumentationOwner und Code Files sind in der Namenssuche enthalten (als elementType-Filter AccessUnit, Datasource, DocumentationOwner, CodeFile).

fs_search_documentation durchsucht MLDoc-Felder auf Metadatatypes, Component-Properties, Forms und DocumentationOwnern. Die Suche findet Doku-Inhalte; den Namen eines DocumentationOwners findet man über fs_search_names. Die FrameworkStudio-Hilfe durchsucht sie nicht — dafür gibt es fs_search_help (siehe unten).

Hilfe und API-Referenz

Die FrameworkStudio-Hilfe (Konzepte, Anleitungen, Release Notes) ist im MCP-Server enthalten und passt damit immer zur Version der IDE. Die API-Referenz wird aus den XML-Dokumentationen gelesen, die mit FrameworkStudio ausgeliefert werden. Beide stehen ohne Internetzugang zur Verfügung.

Tool Beschreibung
fs_search_help Volltextsuche in der Hilfe. Parameter: query, regex (optional, Default false), caseSensitive (optional, Default false), maxResults (optional, Default 50 Trefferzeilen). Ohne regex wird die Anfrage an Leerzeichen in Begriffe zerlegt, "…" hält eine Phrase zusammen; eine Seite trifft, wenn alle Begriffe auf ihr vorkommen (nicht unbedingt in derselben Zeile). Mit regex wird der Ausdruck zeilenweise geprüft. Seiten mit Treffer im Titel stehen vorn, danach nach Trefferzahl. Die Tool-Beschreibung nennt die Themen der Hilfe (oberste Ebene des Inhaltsverzeichnisses), damit der KI-Client weiß, welche Bereiche abgedeckt sind.
fs_get_help Hilfe lesen. Parameter: page (optional, z.B. doc/konzepte/dependency-injection), section (optional, z.B. doc/print-server, nicht zusammen mit page), offset, limit (optional). Ohne page und section kommt die Liste aller Seiten, mit section die Gliederung eines Bereichs, mit page der Markdown-Inhalt einer Seite (Details siehe unten).
fs_get_api Veröffentlichte API-Referenz nachschlagen — dieselben Typen und Member wie in der Online-API-Doku (mit [DocfxBrowsable] markiert, aus FS.Shared, FS.Hosting.*, FS.DataClient, FrameworkStudio.General und FSDeveloperAPI). Parameter: name, maxResults (optional, Default 50). name ist eine UID wie FS.Hosting.Shared.FSServiceProvider.CreateScope oder deren Ende (FSServiceProvider.CreateScope, CreateScope), optional mit Parameterliste oder Präfix T:/M:/P:/F:/E:; Groß-/Kleinschreibung und ein Generik-Suffix wie `2 sind optional.

Ergebnisse von fs_search_help

Jeder Treffer enthält:

  • page — Seiten-ID, mit fs_get_help lesbar
  • title — Titel der Seite
  • heading — nächste Überschrift oberhalb der Zeile (leer vor der ersten Überschrift)
  • lineNumber — 1-basiert, passend zur Nummerierung von fs_get_help
  • matchLine — die Trefferzeile; Zeilen mit mehr als 200 Zeichen werden um den Treffer herum gekürzt (… markiert die Kürzung)
  • url — Link zur Online-Doku (leer bei toc.yml)

Ergebnisse von fs_get_help

Der Weg zu einer Seite führt vom Thema über den Bereich (den Ordner, z.B. Thema „Print-Server“ → doc/print-server) und dessen Gliederung zur Seite:

Aufruf Ergebnis
ohne page und section Liste aller Seiten mit page und title; offset und limit zählen dann Seiten statt Zeilen. Mit offset 1 zusätzlich sections, die Bereiche der Hilfe; limit 1 liefert nur die Bereiche ohne die lange Seitenliste.
mit section Gliederung des Bereichs: je Seite page, title und outline (die H2/H3-Überschriften mit ihrer Zeilennummer), dazu subsections. Nur Seiten direkt im Ordner; offset und limit zählen Seiten (Default 50).
mit page Markdown-Inhalt der Seite (inkl. Front Matter), jede Zeile mit Zeilennummer (passend zu lineNumber aus fs_search_help). Lange Seiten werden nach limit Zeilen gekürzt (Default 500, truncated) und mit offset = bisheriger Offset + limit fortgesetzt.
  • Die Seiten-ID ist tolerant: .md, .html, #anker, führendes docs/ und Groß-/Kleinschreibung sind egal.
  • Bei einer unbekannten Seite schlägt die Fehlermeldung ähnliche Seiten vor.
  • Das Inhaltsverzeichnis ist als Seite doc/toc.yml abrufbar (außerdem toc.yml und articles/toc.yml); es hilft bei der Navigation, wenn eine Suche nichts findet.

Ergebnisse von fs_get_api

  • Eindeutiger Treffer: name, kind, assembly, url (Online-API-Seite), helpPages (Hilfeseiten, die auf diese API verweisen — lesbar mit fs_get_help, lineNumber ist die verweisende Zeile) und entries je Überladung mit uid, returnType, obsolete und der XML-Dokumentation. Eine Parameterliste im name wählt die passende Überladung, ein leeres () die parameterlose; passt keine, kommen alle Überladungen mit einem Hinweis (note).
  • Typen liefern zusätzlich baseType, interfaces und die selbst deklarierten members. Geerbte Member stehen beim Basistyp und lassen sich dort mit fs_get_api nachschlagen.
  • Mehrere Treffer: candidates mit uid, kind, Zahl der Überladungen und Kurzbeschreibung — anschließend mit der uid des passenden Kandidaten erneut aufrufen.
  • <inheritdoc/> wird nicht aufgelöst; die Dokumentation steht dann beim Basistyp bzw. Interface-Member.
  • docsMissing / loadErrors nennen Assemblies, deren Dokumentation nicht verfügbar ist.
Note

fs_get_api kennt nur API mit XML-Dokumentation (///-Kommentar). Ein fehlender Treffer beweist daher nicht, dass es die API nicht gibt.

Tip

Der MCP-Server gibt KI-Clients beim Verbindungsaufbau einen Hinweis mit (instructions): Bevor das Modell das Verhalten von FrameworkStudio aus Code oder aus fehlenden Suchtreffern ableitet, soll es die Hilfe (fs_search_help, fs_get_help) und die API-Referenz (fs_get_api) befragen. Die url aus den Treffern kann an den Benutzer weitergegeben werden, wenn er in der Online-Doku weiterlesen soll.

Änderungshistorie und Vererbung

Tool Beschreibung
fs_get_element_history Versionsverlauf eines Elements (Version, Datum, Benutzer, Kommentar, Check-out-Status) — für Namespace-Elemente wie Components, Forms und Services ebenso wie für DB-Tabellen. Parameter: fullName, maxResults (optional, Default 50 — es werden die neuesten Versionen zurückgegeben; totalVersions nennt die Gesamtzahl, truncated zeigt eine Kürzung an).
fs_get_method_history Code-Änderungen einer Methode über verschiedene Versionen, wie im Method History Browser der IDE. Parameter: fullName, methodName, declaration (bei Überladungen, siehe Methoden adressieren), label, sinceLabel, includeOlderLabels, maxResults (optional, Default 50 — gezählt werden Versionen mit tatsächlicher Änderung). Die Historie wird von der neuesten Änderung rückwärts gesammelt und endet nach maxResults Änderungen; kleine Werte sind daher auch bei Elementen mit vielen Versionen schnell. truncated zeigt ältere Änderungen an; versionsWithChanges (Gesamtzahl) ist nur gesetzt, wenn alle Versionen betrachtet wurden.
fs_get_element_changelog CheckIn-Verlauf eines Elements über mehrere Labels, je Version mit der Liste der geänderten Methoden (Name, Signatur, Status added/modified/deleted) — ohne Methoden-Code. Parameter: fullName, label, sinceLabel, includeOlderLabels, methodFilter, includeDeclarations. Die älteste Version des Bereichs ist die Ausgangsbasis (isBaseline) ohne Methodenliste. Nur Labels ab FrameworkStudio 3.7 werden ausgewertet (siehe unten).
fs_diff_method Unified-Diff einer einzelnen Methode zwischen zwei Labels bzw. zwei Element-Versionen. Parameter: fullName, methodName, declaration (bei Überladungen), labelA, labelB, versionA/versionB (optional, Default jeweils die neueste Version im Label), context (Default 3 Zeilen). labelA und labelB dürfen gleich sein, um zwei CheckIns innerhalb eines Releases zu vergleichen.
fs_get_checkin_history Globaler CheckIn-Verlauf (wer hat wann was eingecheckt). Parameter: sinceDate (optional, ISO-Format, Default: letzte 30 Tage), user (optional, Teilstring, ohne Groß-/Kleinschreibung), elementType (optional, z.B. Component), includeCheckedOut (optional, auch aktuell ausgecheckte Elemente, Default false), packageScope, maxResults (optional, Default 100). Jedes Package der Hierarchie liefert die CheckIns seines aktuellen Labels; packageName nennt das Package.
fs_get_inheritance_tree Vererbungsbaum eines Elements: Vorfahren (Basis-Kette) und/oder Nachfahren (Ableitungen). Parameter: fullName, direction (ancestors|descendants|both, Default both), maxDepth (Default 50). Vererbung gibt es bei Forms, Metadatentypen, Reports und Workflows. Die Customizing-Kette über Packages ist nicht enthalten — eine Element-Version aus einem Basis-Package liefert fs_get_devobject mit package.
Tip

Für die Frage „was hat sich zwischen zwei Releases geändert“ ist fs_get_element_changelog der token-sparsame Einstieg (Methodenlisten ohne Code); für die interessanten Treffer anschließend gezielt fs_diff_method aufrufen, statt ganze Historien über fs_get_method_history zu laden.

Welche Labels gelesen werden

Die History-Tools lesen die Labels des Packages, zu dem das Element gehört — wie der Versionsbrowser der IDE:

  • Für ein nicht angepasstes Element aus einem Basis-Package sind das die Labels des Basis-Packages, für eine Customization die Versionen der Customization.
  • Ohne Angabe von label wird das Label des Packages in der aktiven Hierarchie verwendet (für Elemente des aktiven Packages also das aktive Label).
  • Ist dieses Label nicht verfügbar, wird das letzte Label gelesen und note weist darauf hin.

Historie importierter Packages

Beim Export eines Packages wird je Label nur die aktuelle Version eines Elements mitgenommen. Ein importiertes Package (z.B. ein ausgeliefertes Basis-Package) enthält deshalb je Import und Label nur einen Stand; die einzelnen CheckIns dazwischen fehlen.

Lesen die History-Tools (fs_get_element_history, fs_get_method_history, fs_get_element_changelog, fs_diff_method, fs_get_checkin_history) ein solches Package, setzen sie historyAvailable: false und nennen das Package in note. Die gelieferten Versionen sind dann die importierten Stände, nicht die vollständige Historie. Das mit FrameworkStudio ausgelieferte SystemPackage zählt nicht als importiert.

Changelog erst ab Labels mit FS 3.7

Ob eine Methode in einer Element-Version geändert wurde, erkennt fs_get_element_changelog an der Versionszuordnung der Methoden, die es erst seit FrameworkStudio 3.6 gibt. In älteren Labels würde sonst jede Methode in jeder Version als geändert gemeldet. Der Changelog liest deshalb nur Labels ab FS 3.7:

  • Liegt das angefragte label davor, endet der Aufruf mit einem Fehler, der auf fs_get_method_history verweist.
  • Ältere Labels werden übersprungen, auch wenn sinceLabel darunter liegt. coveredFromLabel nennt dann das älteste tatsächlich gelesene Label, note weist auf das Überspringen hin.

Ältere Stände einer Methode liefern fs_get_method_history und fs_diff_method; beide vergleichen den Code direkt und sind von dieser Grenze nicht betroffen.

Note

Bei Elementen mit langer Historie (viele Versionen, viele Labels) den Changelog nicht auf einmal anfordern, sondern in Abschnitten — z.B. wenige Releases pro Aufruf über sinceLabel und label. Ein einzelner Aufruf darf die IDE höchstens 30 Sekunden belegen (siehe Zeitlimits).

Zeitlimits

Die Tools lesen das Repository über die IDE. Damit ein MCP-Aufruf die IDE nicht blockiert, gelten zwei Grenzen:

  • Wartezeit: Ist die IDE beschäftigt und kann ein Aufruf nicht innerhalb von 30 Sekunden starten, wird er verworfen (Meldung „The IDE's UI thread is busy …“ mit der Zahl der wartenden Aufrufe). Abhilfe: später erneut versuchen und Aufrufe nacheinander statt parallel senden.
  • Laufzeit: Ein Aufruf darf die IDE höchstens 30 Sekunden belegen. Die History-Tools (fs_get_method_history, fs_get_element_changelog) brechen danach ab und geben die IDE wieder frei. Abhilfe: den Bereich enger wählen (label/sinceLabel, kleineres maxResults).

Die aufwendige Auswertung (z.B. das Auswerten der Methodensignaturen für fs_search_code, die Hilfe- und API-Tools) läuft außerhalb der IDE-Oberfläche und zählt nicht gegen diese Grenzen.

Hinweise zur Nutzung

  • Für große Components (50+ Properties, 30+ Methoden) ist detail=summary effizienter als detail=full. Summary zeigt die Struktur ohne Code-Bodies.
  • Mit dem Parameter method lässt sich gezielt eine einzelne Methode mit vollem Code laden statt die ganze Component.
  • Mit dem Parameter property lässt sich gezielt eine einzelne Property auslesen statt die ganze Component.
  • Collections sind Components mit ComponentType=Collection — sie erscheinen in fs_list mit elementType=component, nicht in einer separaten Liste.
  • fs_search_dependencies zeigt, was ein Element referenziert — nicht, welche Elemente das Element referenzieren. Für die Gegenrichtung fs_search_code verwenden.
  • Der Such-Cache (fs_search_names, fs_search_code, fs_search_documentation) wird bei einem Label-Wechsel sowie nach Ablauf einer Gültigkeitsdauer von 5 Minuten neu aufgebaut. Ein CheckIn innerhalb desselben Labels wird also erst mit dem nächsten Cache-Aufbau sichtbar — ein Neustart des MCP-Servers ist dafür nicht nötig.
  • Ausnahme Code Files: Änderungen in einem offenen Code-File-Editor sind in fs_search_code bereits ca. 1 Sekunde nach der letzten Eingabe suchbar — auch wenn sie noch nicht eingecheckt sind. Check-out, Check-in und Undo-Checkout eines Elements bauen den Code-File-Index beim nächsten Suchaufruf neu auf. Methoden-Änderungen in Components, Forms usw. werden dagegen erst nach bis zu 5 Minuten sichtbar.
  • Alle drei Suchtools geben indexedAt (UTC) und indexedLabel mit aus — den Zeitpunkt des Indexaufbaus und das indizierte Label. Bei fs_search_code ist indexedAt der ältere der beiden Aufbauzeitpunkte (Methoden- und Code-File-Index). Ein Leerergebnis bedeutet damit nachvollziehbar „nicht in diesem Index“ statt „existiert nicht“.
  • Fragen zum Verhalten von FrameworkStudio (Konzepte, Konfiguration, APIs) zuerst über fs_search_help/fs_get_help und fs_get_api klären, statt sie aus dem Repository-Code abzuleiten. Die Hilfe ist auf Deutsch: deutsche Suchbegriffe verwenden; Bezeichner wie IFSServiceRegistrar funktionieren unverändert.
